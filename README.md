## 1. プロジェクト概要・背景

自身の所属するアカペラサークルで実際に発生していた、
「複数日程」「リハーサル」「出演者の複数バンド掛け持ち」を考慮したスケジュール作成の難しさを解決するために開発した、個人開発のWebアプリです。

従来の手作業やスプレッドシート中心の運用では、出演時間の重複や配置ミスなどのヒューマンエラーが発生しやすく、作成者への負荷も大きい課題がありました。
本アプリでは、直感的なドラッグ＆ドロップUIとリアルタイム制約チェックにより、運用上のミスを未然に防ぐことを主目的としています。

## 2. 使用技術 (Tech Stack)

- **フロントエンド:** TypeScript, React, Vite
- **UI / スタイリング:** Tailwind CSS, dnd-kit
- **バックエンド / データベース:** Firebase (Firestore / Authentication), Node.js (Firebase Admin SDK)
- **インフラ / デプロイ:** Vercel (Vercel Functions / Serverless API)
- **ソースコード管理:** GitHub

## 3. 💡 AI活用と開発の工夫

本プロジェクトでは、開発スピードだけでなく実装品質を高めるため、AIを「要件整理」「設計検討」「実装補助」に一貫して活用しました。
その結果、自身はドラッグ＆ドロップ時の状態整合性やユーザー体験など、難易度の高いコア部分へ集中できました。

- **制約チェックロジックの短期構築**
  - 「出演時間帯の超過」「同一クール内重複」「連続出演」などの複雑な判定を、自然言語でAIと壁打ちしながら設計。
  - エッジケースの洗い出しと判定順序の最適化を早期に進め、バグの少ない実装を短期間で構築。
- **セキュアなアクセス設計**
  - 共有URLの読み取り専用アクセス、PAT発行フロー、Firestoreセキュリティルールを組み合わせた認可設計を実施。
  - AIの知見を取り入れ、実装容易性とセキュリティのバランスを保った構成に整理。
- **UI開発効率の最大化**
  - Tailwind CSSベースの固定ヘッダーや3ペイン構成のモックアップ作成をAIで高速化。
  - 浮いた工数を、D&D時の状態管理や操作フィードバック最適化といったUXの要所に再投資。

<details>
<summary><b>4-2. 主要機能仕様（複雑なスケジューリング課題への対応）</b></summary>

### 仕様の全体像
- **イベント管理（F-01 / F-11）:** イベント情報、本番日/リハ日、プリセット等の設定管理
- **バンド管理（F-02 / F-05）:** 演奏時間、出演回数、メンバー、出演可能時間帯
- **編集体験（F-03 / F-04）:** 本番/リハ切替、日別切替、クール構造、D&D並び替え
- **制約チェック（F-06）:** 重大度付きの違反可視化
- **拡張機能（F-07 / F-12）:** カスタム列、セル結合、長期運用向け設定

### 制約チェックの詳細
- **高:** 出演可能時間帯外への配置
- **中:** 同一クール内での同一バンド重複
- **低:** メンバー重複バンドの連続出演
- 行ハイライト、警告アイコン、サマリーパネルで即時に問題箇所を特定可能

### リハーサル仕様
- 形式は以下の3種類（混在不可）
  - 別日リハーサル
  - クール直前リハーサル
  - 当日一括リハーサル
- 本番タイムテーブルとの連動を含む自動追加ロジックを実装

### 採用担当向け要点
- 単純なCRUDではなく、**制約が多い運用ドメイン**をUI・ロジック・データ構造で統合的に解決。

</details>

<details>
<summary><b>4-3. API仕様（UI併用のユーザー本人向け自動化）</b></summary>

### 設計方針
- 外部パートナー向け公開APIではなく、**認証済みユーザー本人がUIと併用するAPI**として設計
- 最小権限・監査可能性・冪等性を重視

### 主要エンドポイント
- `POST /api/v1/bands`
- `POST /api/v1/user-api-tokens`
- `GET /api/v1/user-api-tokens`
- `PATCH /api/v1/user-api-tokens?tokenId=...`
- `DELETE /api/v1/user-api-tokens?tokenId=...`

### 認証・認可
- `POST /api/v1/bands`
  - `Authorization: Bearer <Firebase ID Token>`
  - または `x-user-api-token: <pat_...>`
- トークン管理APIは Firebase IDトークンのみ
- `eventId` 単位でアクセス制御（owner/editor もしくは PAT スコープ）

### 安全性と運用性
- **冪等性:** `x-idempotency-key`（必須）
- **PAT管理:** 平文保存せずハッシュ保存
- **運用コレクション:** `userApiTokens`, `apiIdempotency`, `apiRateLimits`, `apiRequests`
- **主要レスポンス:** `201`, `200`, `400`, `401`, `403`, `409`, `429`

### ローカル検証
```bash
FIREBASE_ID_TOKEN=<Firebase ID Token> node test-api-user.cjs
```

### 本番運用（トークン失効）
1. 対象トークンを失効
2. 監査ログで影響確認
3. 最小権限で再発行
4. 連携先切替
5. 失効理由・担当者・時刻を記録

</details>

<details>
<summary><b>4-4. 認証フロー仕様（仮登録 → 本登録）</b></summary>

### フロー概要
- メール登録は「仮登録（確認メール送信）」→「本登録（確認後ログイン）」の2段階
- Googleログインユーザーは password provider 未連携時に `/set-password` へ遷移

### 追加API
- `POST /api/v1/auth/register-pending`
- `POST /api/v1/auth/register-resend`
- `POST /api/v1/auth/register-confirm`

### 実装済みポイント
- `registrationPendings` で `pending/completed` を管理
- `register-confirm` で `emailVerified` を検証し本登録確定
- `firestore.rules` で `registrationPendings` のクライアント直接アクセスを禁止

### 現在の制約と次フェーズ
- 確認リンク生成まで実装済み（メール配信基盤接続は次フェーズ）
- 再送レート制限、期限切れUI、認証E2E自動化が今後の重点タスク

</details>
